# BlueSapphire 重构保护性收口设计

日期：2026-07-22

阶段：第一阶段

状态：待用户书面审阅

## 1. 背景

BlueSapphire 当前工作区包含一轮尚未提交的大规模重构：76 个已跟踪文件发生变化、5 个已跟踪文件被删除、41 个文件尚未跟踪，已跟踪差异约为 6,176 行新增和 2,781 行删除。重构覆盖 Cleaner 安全执行、AI 工具 Provider、WinUI 原生界面、主题系统和开发日志隔离。

当前代码已经通过 215 项自动化测试、无增量零警告构建，并可启动真实 WinUI 清理助手窗口后正常关闭。但是，工作区尚未形成可回滚检查点，而且 `Assets/DevMatrixLog.json` 的正式历史节点已被两个占位节点覆盖，违反项目的 append-only 红线。

因此，在继续拆分 Cleaner、AI 或 UI 架构前，先建立一个不改变产品行为的保护性基线。

## 2. 目标

本阶段必须完成以下目标：

1. 恢复 Git `HEAD` 中原有的正式开发日志历史，删除确认属于污染数据的 `seed-100` 和 `seed-101`。
2. 确保运行时开发日志只写入应用数据目录，不再同步或反写项目源码目录。
3. 用自动化测试保护正式开发日志历史和源码隔离约束。
4. 将未跟踪文件分类，避免核心源码丢失，也避免安装包、构建产物和本地工具缓存进入普通源码提交。
5. 保持当前 Cleaner、AI、媒体和 UI 的产品行为不变。
6. 完成全量测试、零警告构建和真实 WinUI 启动/正常关闭验证。
7. 为后续重构形成范围清晰、可回滚的 Git 检查点。

## 3. 非目标

本阶段不做以下工作：

- 不增加或删除 Cleaner 扫描规则。
- 不改变风险等级、默认选择、永久删除、隔离或系统清理策略。
- 不重构 `AIToolsRegistry`、`CleanerScanService` 或 `CleanerExecutionService`。
- 不调整页面布局、主题视觉或交互流程。
- 不修改媒体处理算法。
- 不发布安装包，不更新应用版本号。
- 不把“构建和测试通过”描述为全部真实清理流程已经完成。

## 4. 开发日志恢复设计

### 4.1 权威来源

Git `HEAD:Assets/DevMatrixLog.json` 是恢复已有正式历史节点的权威来源。当前工作区中的 `seed-100` 和 `seed-101` 已由用户确认属于污染数据，不作为正式历史保留。

恢复时必须满足：

- `HEAD` 中原有节点的 `Id`、`Version`、`Title`、`Description`、`FullContent` 逐字段保持不变。
- 本阶段不伪造新的版本记录。
- 后续新增正式记录只能追加到 JSON 数组末尾。
- 不允许通过重新排序、去重、格式迁移或字符编码转换间接改变历史业务字段。

### 4.2 运行时写入边界

`DevLogDataService` 的运行时数据文件继续位于应用数据根目录或测试传入的隔离根目录。保存流程可以：

- 更新运行时数据文件；
- 创建运行时备份；
- 在测试临时目录中读写。

保存流程不得：

- 向上遍历寻找 `BlueSapphire.csproj`；
- 将运行时文件复制到项目 `Assets`；
- 根据 Debug/Release 配置改变源码保护边界；
- 修改 `Assets/DevMatrixLog.json`。

## 5. 自动化保护设计

采用先失败、后修复的测试驱动顺序。

### 5.1 正式历史不变量测试

新增或扩展测试，读取：

- Git/项目基线中应存在的正式历史节点；
- 当前 `Assets/DevMatrixLog.json`。

测试至少验证：

1. 正式节点仍存在。
2. 受保护字段完全一致。
3. 正式节点顺序没有变化。
4. 不存在 `seed-100`、`seed-101` 污染节点。
5. JSON 可以正常解析。

测试不得依赖当前损坏文件自动生成“期望值”，否则无法发现历史被一起改写。

### 5.2 源码隔离行为测试

使用受控临时目录创建 `DevLogDataService`，执行新增、编辑或保存操作，然后比较操作前后的源码文件哈希和内容。

测试必须证明：

- 运行时文件发生预期变化；
- 项目 `Assets/DevMatrixLog.json` 未发生变化；
- 即使测试运行在项目输出目录下，也不会发现并反写源码目录。

现有 `DevLogSourceIsolationTests` 的源码文本检查可作为补充，但不能替代行为测试。

### 5.3 追加语义测试

对开发日志集合的正式写入模型验证：

- 新记录追加在末尾；
- 旧记录受保护字段不变；
- 编辑或删除历史记录的现有产品能力如果仍被保留，必须明确仅作用于运行时副本，不能修改源码基线。

## 6. 未跟踪文件分类设计

所有未跟踪文件分为四类：

### A. 核心源码与测试

应纳入后续对应功能提交，例如：

- `Services/CleanerOperationCoordinator.cs`
- `Services/CleanerSystemCleanupService.cs`
- `Services/AIToolCapabilityCatalog.cs`
- `Services/*AIToolActionProvider.cs`
- 新增的 Cleaner、AI 和开发日志测试

这些文件不得被清理或忽略。

### B. 正式项目文档

设计、验收和架构文档应按所属阶段提交，但文档中的“通过”必须有当前验证证据支持。

### C. 本地协作配置

`.trae/`、`.workbuddy/` 等目录需要单独判断是否属于团队共享约定。第一阶段只分类，不在未经确认的情况下批量删除。

`.agents/AGENTS.md` 是当前项目规则来源，必须保留，是否纳入仓库由独立 Git 卫生决策处理。

### D. 生成物和发布二进制

`Output/*.exe`、`bin/`、`obj/`、`artifacts/`、`AppPackages/` 等不作为普通源码修改提交。若未来需要发布安装包，应通过专门发布流程或 GitHub Release 管理。

## 7. Git 收口策略

采用小范围、可审查提交，不执行 `git reset --hard`、`git clean` 或批量覆盖用户改动。

建议检查点：

1. 设计文档提交。
2. 开发日志历史恢复与隔离测试提交。
3. Git 忽略规则与未跟踪文件分类提交。
4. 后续 Cleaner、AI、UI 分别建立独立提交。

每次提交只暂存明确列出的文件，提交前检查 staged diff，避免把当前大规模工作区意外一次性提交。

## 8. 验收矩阵

| 用户/开发动作 | 期望状态 | 责任模块 | 自动化证明 | 真实证明 |
|---|---|---|---|---|
| 读取开发日志源码基线 | 原正式节点存在且字段不变 | `Assets/DevMatrixLog.json` | 历史不变量测试 | 人工核对 Git diff |
| 运行时新增日志 | 只更新应用数据目录 | `DevLogDataService` | 临时目录行为测试 | 启动应用后核对源码哈希 |
| 运行时编辑/删除日志 | 不修改源码基线 | `DevLogDataService` | 源码隔离测试 | 核对工作区状态 |
| 执行全量测试 | 不污染源码文件 | 测试程序集 | 215 项及以上通过 | 测试前后 Git diff 对比 |
| 构建应用 | 0 警告、0 错误 | 解决方案 | 无增量构建 | 构建输出核对 |
| 启动清理助手 | 窗口句柄非零且可响应 | WinUI 生命周期 | 不适用 | `Responding=True` |
| 正常关闭窗口 | 进程正常退出 | 主窗口生命周期 | 相关测试 | 正常关闭且退出码为 0 |

## 9. 失败与回滚

- 如果恢复后测试揭示现有功能依赖污染节点，停止继续修补，先定位依赖来源，不重新加入污染节点绕过失败。
- 如果运行时保存仍能修改源码，保留失败测试并追踪实际路径解析链路。
- 如果 Git 忽略调整会隐藏核心源码，立即撤销该条规则，不使用宽泛目录或扩展名忽略。
- 所有回滚只针对本阶段明确修改的文件，不覆盖工作区其他未提交重构。

## 10. 完成标准

本阶段只有同时满足以下条件才可完成：

1. 正式开发日志历史恢复，污染节点消失。
2. 历史受保护字段与 Git 基线一致。
3. 运行时保存不会修改项目源码日志。
4. 相关回归测试先观察到预期失败，再在修复后通过。
5. 全量测试不少于 215 项且零失败。
6. `dotnet build BlueSapphire.slnx --no-incremental --no-restore -v:minimal` 为零警告、零错误。
7. 真实 x64 WinUI 清理助手窗口可响应，并能通过正常关闭请求退出。
8. 工作区中核心未跟踪源码没有丢失，生成物没有混入源码提交。
9. 最终报告明确列出本阶段未触及的 Cleaner 真实文件系统路径和后续重构范围。
